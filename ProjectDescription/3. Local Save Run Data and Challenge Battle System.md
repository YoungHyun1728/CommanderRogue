## 3.  JSON 로컬 저장 + PlayFab을 이용한 챌린지모드 구현(PvP형 PvE)

이 문서에서는 CommanderRogue의 런 진행 데이터를 JSON으로 로컬 저장하는 구조와, 클리어한 파티를 PlayFab에 업로드해 다른 유저의 파티와 비동기적으로 겨루는 챌린지 모드 구조를 설명합니다.

이 프로젝트의 챌린지 모드는 실시간 PvP가 아니라 `상대 파티의 스냅샷을 받아 AI 적군으로 재구성한 뒤 싸우는 PvP형 PvE` 방식입니다.  
즉, 플레이어는 다른 유저의 현재 접속 상태와 무관하게 저장된 파티 데이터를 상대로 전투하며, 서버는 상대 파티 스냅샷을 중개하는 역할을 맡습니다.

#### 관련 클래스

<img width="1149" height="739" alt="image" src="https://github.com/user-attachments/assets/2c185152-3acb-4176-bc69-e870bdc54a50" />

- `RunManager`는 실제 전투, 맵 진행, 파티 상태를 들고 있는 런타임 오브젝트다.
- `RunSaveCoordinator`는 `RunManager`의 현재 상태를 `SaveData`로 변환하거나, 반대로 `SaveData`를 읽어 런타임 상태로 복원한다.
- `SaveManager`는 직렬화된 JSON을 `Application.persistentDataPath`에 저장하고 다시 읽어오는 파일 I/O 전담 클래스다.
- `SaveData`, `NodeData`, `PlayerUnitState`, `PendingDebuffState`는 Unity의 `JsonUtility`로 직렬화하기 쉬운 순수 데이터 객체로 구성되어 있습니다.

이렇게 분리한 이유는 `게임 진행 로직`과 `저장 포맷`, `파일 처리`를 섞지 않기 위해서입니다.  
저장 규칙이 바뀌더라도 `SaveManager`와 `SaveData` 계층에서 수정 범위를 제한할 수 있고, 런타임 로직은 `RunManager` 쪽에 그대로 유지할 수 있습니다.

이 다이어그램은 챌린지 모드에서 `현재 내 파티를 스냅샷으로 만드는 단계`, `로컬/서버 저장 단계`, `상대 파티를 받아 전투에 투입하는 단계`를 보여준다.

- `ChallengeSnapshotBuilder`는 현재 런의 파티를 읽어 `ChallengePartySnapshot`으로 변환합니다.
- `ChallengeService`는 스냅샷을 로컬 JSON 파일에 보관하고, PlayFab CloudScript로 업로드하거나 서버 목록을 받아오는 통신 창구 역할을 한다.
- `RunChallengeCoordinator`는 챌린지 모드 활성화, 상대 파티 큐 관리, 서버 실패 시 로컬 폴백, 적 스폰 요청까지 전체 흐름을 관리합니다.
  
덕분에 일반 런 진행과 챌린지 모드가 같은 전투 시스템을 공유하면서도 데이터 수급 방식만 다르게 유지된다.

### 작동흐름

### 1. 로컬 저장 구조

현재 구현에서 런 저장은 `SaveData.json` 파일 하나를 기준으로 동작하며, 저장 시점마다 `SaveData_yyyyMMdd_HHmmss.json` 백업도 함께 남긴다.

저장되는 핵심 데이터는 다음과 같다.

- `SaveData`
  현재 라운드, 골드, 바이옴, 리롤 횟수, 누적 처치 수, 다음 전투 난이도 보정치, 장신구 보너스, 파티 유닛 상태, 맵 노드 진행 상태를 모두 담는다.
- `NodeData`
  맵 노드의 레벨, 인덱스, 타입, 연결 관계와 함께 클릭 여부, 현재 위치 여부, 해결 여부, 해결된 이벤트 ID를 보존한다.
- `PlayerUnitState`
  유닛 원본 ID, 레벨, 경험치, HP/MP, 배치 좌표, 생존 여부, 장착 장비 이름 목록을 저장한다.
- `PendingDebuffState`
  다음 전투 시작 시 파티 전체에 적용될 디버프를 저장한다.

이 정보만 저장하면, 맵 위 어느 지점에서 중단했는지와 현재 파티의 실질적인 전투 상태를 다시 복원할 수 있다.

### 2. 로컬 저장 동작 흐름

#### 저장

1. 전투나 이벤트가 끝나고 맵으로 복귀할 때 `RunManager.GoToNextRound()`가 호출된다.
2. 내부적으로 `RunSaveCoordinator.GoToNextRound()`가 실행된다.
3. `RunSaveCoordinator.BuildSaveData()`가 현재 `RunManager`, `MapGenerator`, 파티 유닛, 디버프 상태를 `SaveData`로 변환한다.
4. 변환된 데이터는 `SaveManager.SaveGame()`으로 전달된다.
5. `SaveManager`는 `JsonUtility.ToJson()`으로 직렬화한 뒤 `Application.persistentDataPath/SaveData.json`에 저장한다.

즉, 이 프로젝트는 `상시 자동 저장`보다는 `라운드 종료 후 맵 복귀 시점 저장` 정책을 사용한다.  
설정창에서 타이틀로 돌아가는 `SaveAndReturnToTitle()`는 현재 추가 저장 없이 타이틀로만 이동하도록 구현되어 있다.

#### 불러오기

1. 타이틀 화면에서 `StartSceneUI.OnClickContinue()`가 호출된다.
2. `SaveManager.LoadGame()`이 `SaveData.json`을 읽어 `saveData`를 메모리에 올린다.
3. 게임 씬 진입 후 `RunManager.Start()`에서 `SaveManager.instance.HasPendingRunLoad`를 검사한다.
4. 저장 데이터가 유효하면 `RunSaveCoordinator.RestoreRun()`이 실행된다.
5. 이 과정에서 기존 유닛을 정리하고, 저장된 `PlayerUnitState`를 기준으로 파티 유닛을 다시 스폰한 뒤 장비와 스탯, 타일 위치를 복구한다.
6. 마지막으로 맵 점유 정보와 바이옴 지속 효과를 다시 적용하고 맵 화면으로 복귀한다.

이 복원 과정 덕분에 단순히 수치만 읽는 것이 아니라, `어느 유닛이 어느 칸에 서 있었는지`까지 이어서 플레이할 수 있다.

#### 세이브 삭제

- `새 게임 시작`
- `게임 오버`
- `게임 클리어`

위 상황에서는 `SaveManager.DeleteSaveFiles()`를 호출해 기존 런 세이브와 백업 파일을 정리한다.  
즉, 저장 파일은 `현재 진행 중인 런`을 이어가기 위한 데이터이며, 종료된 런 기록을 영구 보관하기 위한 구조는 아니다.

### 3. 챌린지 모드 데이터 구조

챌린지 모드에서는 런 전체를 저장하지 않고, `상대가 전투에 사용할 정보만 추린 파티 스냅샷`을 저장한다.

- `ChallengePartySnapshot`
  파티 ID, 생성자 ID, 파티 이름, 클리어 라운드, 파티 전투력, 생성 시각, 유닛 목록을 가진다.
- `ChallengeUnitSnapshot`
  유닛 ID, 표시 이름, 레벨, HP/MP, 배치 좌표, 장비 목록, 그리고 힘/민첩/지능/공격력/공속/이속 같은 전투 재현용 스탯을 저장한다.

여기서 중요한 점은 챌린지용 데이터가 `실시간 전투 상태`가 아니라 `전투 시작 시점의 미러 데이터`라는 것이다.  
상대 유저의 클라이언트와 직접 통신하지 않아도 되므로 구조가 단순하고, 접속 여부와 관계없이 항상 대전을 구성할 수 있다.

### 4. 챌린지 모드 동작 흐름

#### 내 파티 업로드

1. 플레이어가 런 클리어 후 결과 UI에서 챌린지 모드를 요청한다.
2. `RunManager.OnChallengeModeRequested()`가 `RunChallengeCoordinator.TryActivateFromCurrentParty()`를 호출한다.
3. `ChallengeSnapshotBuilder.Build()`가 현재 파티를 `ChallengePartySnapshot`으로 변환한다.
4. 생성된 스냅샷은 `ChallengeService.SaveLocal()`로 먼저 로컬 파일 `challenge_parties.json`에 저장된다.
5. 이어서 `ChallengeService.UploadToPlayFab()`이 PlayFab CloudScript의 `SaveChallenge` 함수를 호출해 서버에도 업로드를 시도한다.

로컬 저장을 먼저 수행하기 때문에, 서버 업로드 실패 시에도 디버그나 폴백용 상대 파티 데이터는 남길 수 있다.

#### 챌린지모드 상대 불러오기

1. 챌린지 맵에서 전투 노드를 선택하면 `RunManager.SelectNode()`가 챌린지 전투인지 검사한다.
2. 챌린지 전투라면 `FetchChallengeAndEnter()` 코루틴이 실행된다.
3. 내부에서 `RunChallengeCoordinator.FetchAndCacheNextOpponent()`가 다음 순서로 상대를 찾는다.
4. 먼저 이미 받아 둔 큐가 있으면 큐에서 바로 꺼낸다.
5. 큐가 비어 있으면 `ChallengeService.GetSnapshotListFromServer()`로 PlayFab CloudScript `GetChallengeList`를 호출한다.
6. 서버 응답이 실패하거나 비어 있으면 `ChallengeService.GetLatestSnapshotExceptParty()`로 로컬 최신 스냅샷을 폴백으로 사용한다.

이 구조 덕분에 네트워크가 불안정해도 챌린지 모드 전체가 막히지 않고, 최소한 로컬 데이터 기반 테스트나 대체 전투는 유지된다.

#### 전투 투입

1. 상대 스냅샷이 캐시되면 `RunManager.EnterReady()`가 호출된다.
2. 일반 전투처럼 랜덤 적을 뽑는 대신, `RunChallengeCoordinator.TrySpawnChallengeEnemies()`가 `EnemySpawnManager.SpawnChallengeEnemies()`를 호출한다.
3. 적 스폰 매니저는 전달받은 `ChallengePartySnapshot`을 읽어 적 유닛 프리팹, 좌표, 장비, 스탯을 복원한다.
4. 이후 전투는 일반 전투와 동일한 `Ready -> Battle -> Reward` 흐름으로 진행된다.

즉, 챌린지 모드는 별도의 전투 시스템을 새로 만든 것이 아니라, `적 생성 소스만 상대 파티 스냅샷으로 교체한 일반 전투의 확장`이라고 볼 수 있다.

### 5. 현재 구조의 장점

- 저장 책임이 `RunManager`, `RunSaveCoordinator`, `SaveManager`로 분리되어 있어 유지보수가 쉽다.
- 챌린지 모드는 실시간 동기화가 필요 없는 비동기 구조라 구현 난이도와 서버 비용을 줄일 수 있다.
- PlayFab 서버 호출이 실패해도 로컬 JSON 기반 폴백이 가능해 개발 단계와 테스트 단계에서 유연하다.
- 일반 전투 시스템을 그대로 재사용하므로, 새로운 모드를 추가하면서도 기존 전투 로직을 크게 훼손하지 않는다.

### 6. 정리

CommanderRogue의 저장 시스템은 `현재 런을 이어서 플레이하기 위한 복원용 저장`에 초점을 맞추고 있고, 챌린지 시스템은 `클리어한 파티를 스냅샷으로 보존하고 다른 플레이어의 파티를 적군처럼 재생성하는 비동기 대전`에 초점을 맞추고 있다.

결과적으로 두 시스템 모두 JSON 직렬화를 기반으로 하지만 목적은 다르다.

- `SaveData`는 내 진행 상황을 복구하기 위한 런 세이브다.
- `ChallengePartySnapshot`은 다른 플레이어와 겨루기 위한 전투용 미러 데이터다.

이러한 분리를 통해 프로젝트는 `싱글 런 진행의 안정성`과 `비동기 경쟁 콘텐츠의 확장성`을 동시에 확보하고 있다.
